# GitHub Copilot CLI Prompt: Add Basic Observability to Workflow-First Semantic MCP Server

Use this Markdown file as the implementation prompt for GitHub Copilot CLI / Copilot agent mode from the root of the repository.

The goal is to add **safe, structured, workflow-aware observability** to an existing MCP server that routes LLM/user requests to governed semantic workflows over Azure SQL Database.

---

## Implementation Prompt

You are acting as a senior backend engineer and observability architect.

I have an existing MCP server that acts as a **workflow-first semantic routing layer** over Azure SQL Database. The server routes user/LLM requests to approved semantic workflows and eventually executes governed SQL templates or validated SQL.

I want to add **basic observability first** so I can inspect the execution path of each request, including:

- incoming MCP request
- MCP tool name and arguments
- workflow candidate retrieval
- workflow routing decision
- prompt composition
- selected system prompt and skill files
- LLM request metadata
- LLM response metadata
- model-requested tool calls, if applicable
- workflow parameter extraction
- semantic context construction
- SQL template rendering
- SQL validation
- SQL execution
- result summarization
- final MCP response
- errors and timings

Important distinction:

The MCP server usually **cannot observe GitHub Copilot's hidden internal prompt**. Do not attempt to introspect Copilot's hidden prompt. The MCP server can only observe:

1. what it receives from the MCP client,
2. what MCP tool calls are made,
3. what the server composes internally for its own LLM calls,
4. what it sends to model providers,
5. what it receives from model providers,
6. what SQL/templates it renders and executes,
7. what responses it returns.

Do not implement fake Copilot prompt introspection. Implement reliable server-side tracing.

## Existing Architectural Context

This project is intended to follow a **workflow-first semantic data architecture**.

Core invariant:

```text
No selected workflow -> no table metadata access -> no SQL generation -> no SQL execution.
```

The LLM should not behave like a generic autonomous SQL agent. It should perform bounded language tasks:

- workflow routing
- parameter extraction
- clarification
- result summarization

Deterministic server code should enforce:

- workflow gating
- metadata allowlisting
- parameter validation
- SQL template selection
- SQL validation
- output contract validation
- authorization checks

Observability must help verify that the server actually follows this architecture.

Every trace should make it easy to answer:

```text
Did the request route through workflow selection first?
Which workflow candidates were found?
Which workflow was selected?
Was a clarification needed?
What prompt did the server compose?
Which prompt assets and skills were included?
Was any raw table metadata exposed too early?
Was SQL rendered from a template or generated by a model?
Was SQL validation successful?
Was the output contract satisfied?
What tool calls happened?
What failed, and where?
```

## High-Level Requirements

Add structured observability without overengineering.

Primary goals:

1. Every MCP request gets a `request_id` and `trace_id`.
2. Every major server step is represented as a span or trace event.
3. Prompt composition is observable in a safe way.
4. LLM calls are observable in a safe way.
5. MCP tool calls are observable.
6. SQL rendering, validation, and execution are observable.
7. Errors are captured with typed error categories.
8. Sensitive data is redacted.
9. Full prompt logging is disabled by default outside local/dev/test.
10. The implementation should be OpenTelemetry-compatible, but it must also work locally without a vendor backend.

Start with:

- local JSONL trace exporter
- structured application logger integration
- optional OpenTelemetry exporter abstraction
- optional Azure Application Insights exporter only if the repository already has Azure Monitor/Application Insights conventions or adding it is straightforward and safe

Do **not** introduce a large observability vendor dependency unless the repo already uses one.

## Critical MCP Logging Rule

If this MCP server uses **stdio transport**, never write logs to stdout.

For stdio MCP servers:

```text
stdout is reserved for JSON-RPC protocol messages.
```

Therefore:

- write diagnostic logs to stderr,
- write structured traces to a file,
- or export through OpenTelemetry,
- but never use stdout logging for diagnostics.

Adapt this to the repository language:

- JavaScript/TypeScript: avoid `console.log` for diagnostics in stdio mode; use `console.error`, file logger, or structured logger to stderr/file.
- Python: avoid `print()` to stdout in stdio mode; use logging configured to stderr/file.
- C#: avoid `Console.WriteLine` for diagnostics in stdio mode; use stderr/file/logger.
- Go: avoid `fmt.Println` / stdout logging in stdio mode; use stderr/file/logger.

Add a test or guard if feasible to ensure stdio mode does not log diagnostics to stdout.

## Final Design Reminder

Do not turn this into a generic autonomous SQL-agent observability system.

Instrument the workflow-first architecture.

The trace should show that:

```text
The LLM does not discover the database.
The LLM discovers approved workflows.

The LLM does not decide joins.
The workflow contract decides joins.

The LLM does not decide report columns.
The output contract decides report columns.

The LLM does not execute SQL.
The server executes validated workflow plans.

The LLM does not enforce governance.
The orchestrator enforces governance.
```

Observability should make violations of these rules obvious.
